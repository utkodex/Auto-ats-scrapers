Question Classification Plan

Auto-ats-scrapers · forms_automation · drafted 2026-10-10

Intention: group every application question stored from Greenhouse forms into classification heads (topics such as Gender or Veteran status). When a form asks a question we have never seen word-for-word, we find which head it belongs to and reuse the answer given for that head last time, so the same thing is never asked twice just because a company phrased it differently.

The idea in one example

“What is your sex?”
“What is your gender?”
“Please select the gender you identify with.”
→
gender

Different wording, one meaning, one head, one stored answer.

Who does what

Head creator

Llama 3.1 8B (local, Ollama)

  • Reads the question database and proposes the initial set of heads.
  • Gives each head a short id, a plain-English description and a few example questions.
  • Does not decide reuse / generate. Testing showed that is unreliable, so code rules set it.
  • Is called again later, only when Jev says a question fits no existing head, and creates a new head for it.

Already in the project: cover_letter.py uses llama3.1:8b through Ollama.

Classifier

Jev (type-safe AI)

  • Takes one question (text, type, options) and the current list of heads.
  • Returns a typed result: exactly one head id from the list, or NO_MATCHING_HEAD.
  • Because the output is typed, it can never invent a head name or return free text.

Flow for a question on a form

The chart shows the main reuse path. The confidence check, the generate-mode heads and the GUI review of new heads are covered in the steps below and under Decisions.

Step by step

  1. Exact match first. The existing QuestionStore.get() lookup stays. No AI is called when the wording is already known.
  2. Jev classifies. For new wording, Jev picks one head from the list, or the escape option NO_MATCHING_HEAD, along with a confidence score.
  3. Check confidence. If the confidence is below the threshold, the user is asked to confirm Jev's pick (or choose another head) before anything is filled.
  4. Check the head's mode.
    • reuse: take the answer last given for that head and fit it to this form's options with Jev (for example “Male” on one form, “Man” on another).
    • generate: essay and “if other, explain” style questions. They are handled like the cover letter: the LLM writes a fresh answer for this job.
  5. No head fits. The question goes to Llama 8B, which drafts a new head (id, description, examples); the mode comes from the rules. The draft appears in the GUI, where the user approves it, edits it, or rejects it. Jev only uses it after approval.
  6. Record it. The question is saved in answers.json with its head and the answer that was used, including generated answers, so there is a full history.

Jev's typed output

The key rule is that Jev can only answer with a head that exists, or say none fits. A sketch of the contract:

class Classification:
    head: Literal["gender", "sexual_orientation", "ethnicity", ..., "NO_MATCHING_HEAD"]
    confidence: float          # 0.0 – 1.0
    reason: str                # one line, for review in the GUI

The allowed values are rebuilt from the head list every time a new head is created, so the type always matches the current heads.

Prompt B (the tested system prompt)

You organise job-application form questions into classification heads.
A head is a topic: questions with different wording but the same meaning share a head
(e.g. "What is your sex?" and "What is your gender?" -> head "gender").
Rules:
- Every question id must be in exactly one head.
- MOST IMPORTANT: a head stores ONE answer. Two questions may share a head ONLY if the
  same person would give the same answer to both. Gender, sexual orientation, ethnicity
  and transgender status have different answers, so they are separate heads.
  University, degree, graduation date, start date and location are separate heads.
  When unsure, make a separate head. One question per head is fine.
- Head ids are short snake_case.
- description: one plain sentence saying what the head is about.
- mode: "reuse" if the same answer can be copied to any company's form,
  "generate" if the answer must be written fresh per job (essays, motivation, "if other, explain" follow-ups).
Return JSON only.

The user message is the JSON list of {id, question, type}. Schema passed as format:

{"type": "object", "required": ["heads"],
 "properties": {"heads": {"type": "array", "items": {
   "type": "object", "required": ["id", "description", "mode", "question_ids"],
   "properties": {
     "id":           {"type": "string"},
     "description":  {"type": "string"},
     "mode":         {"type": "string", "enum": ["reuse", "generate"]},
     "question_ids": {"type": "array", "items": {"type": "integer"}}}}}}}

Scaling

  • The initial run sends all questions in one call. Beyond about 25 questions, send them in batches of about 25, together with the heads created so far, so Llama adds to existing heads instead of starting over.
  • Later, a single new question only reaches Llama when Jev returns NO_MATCHING_HEAD. The same prompt is used, with the current heads included.

Decisions

Each open question from the first draft, with what was decided.

1. Essay and “if other” questions are generated, like the cover letter decided

“This kind of question we will treat as cover letter only. The LLM will generate that and record all the answers with the question.”

  • Jev still classifies these questions, but their head has mode: "generate" instead of "reuse". The mode is set by code rules (see “Mode rules” above), not by Llama, and can be changed in the GUI.
  • For a generate head, the stored answer is never copied. The LLM writes a new answer for each job, the same way cover_letter.py does (Llama 3.1 8B through Ollama), using the job post and, for “if other”, the question before it.
  • Every generated answer is saved with its question and job in answers.json. Earlier answers can be shown to the LLM as style examples, but are not reused as-is.

2. Ask when confidence is low decided

“Yes, need that. If the confidence is not good, ask.”

  • Jev returns a confidence with every pick. Below the threshold (start at 0.75, tunable), nothing is filled silently.
  • The user sees the question, Jev's pick and its one-line reason, and can accept it, choose a different head, or send it to Llama as a new head.
  • The user's choice is saved, so the same wording is an exact match next time and is never asked again.

3. New heads are reviewed and editable in the GUI decided

“Yes, and also give me the option to edit.”

  • A head that Llama creates starts as status: "pending" and appears in the GUI.
  • The user can approve it, edit it (id, description, examples, mode, auto-fill), merge it into an existing head, or reject it.
  • Only approved heads are included in Jev's allowed values. Approved heads stay editable later from the same screen.

4. Jev fits stored answers to the form's options decided

“Yes, do this.”

When the stored answer for a head isn't exactly one of this form's options, Jev is called a second time. This time the allowed values are the form's own options:

class OptionFit:
    option: Literal[*form_options, "NO_GOOD_OPTION"]
    confidence: float

For example, a stored “Male” fits “Man” on another form. NO_GOOD_OPTION or a low confidence goes to the user, using the same rule as decision 2.

5. Storage: a head on each question, plus heads.json decided

“Yes.”

Each question in answers.json gets a head field. All other fields stay as they are.

{ "id": 18, "question": "...", "answer": "...", "type": "...",
  "head": "veteran_status", ... }

A new forms_automation/heads.json holds the heads:

{ "heads": [
  { "id": "veteran_status",
    "description": "Whether the candidate has served in the military",
    "examples": ["Are you a veteran?", "Have you served in the armed forces?"],
    "mode": "reuse",          // "reuse" | "generate", set by rules, editable
    "auto_fill": true,        // false = always ask, even when confident
    "status": "approved",     // "pending" | "approved" | "rejected"
    "created_by": "llama"     // "llama" | "user"
  }
] }
