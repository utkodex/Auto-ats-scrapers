Llama Heads Report

Creating classification heads for the existing Greenhouse question database with Llama 3.1 8B only · 2026-10-10

In short: Llama 8B can create good heads for our 18 questions, but only when two things are true: the prompt clearly says “one head = one answer”, and the temperature is 0. With the plain prompt it lumps unrelated questions together, and at higher temperature its output changes a lot from run to run.

Consistency check: Prompt B at temperature 0 was run 10 more times. The grouping was 18 / 18 in all 10 runs, with the same head names every time. The reuse / generate mode is not reliable: it was 16 / 18 in one run and 13 / 18 in the other nine. So use Llama for grouping and naming, and set the mode with rules and the GUI.

Prompt A vs Prompt B

Prompt A (plain): groups by broad topic

Llama understood “head” as a category, not as one answer. Typical merges:

  • identity = transgender + sexual orientation + ethnicity (3 different answers)
  • previous_employment = current company name + “worked for Datacor before?”
  • education = enrolled? + start/end dates + location + university + degree + graduation date (6 different answers)

Only 7 of 18 questions ended up in a head that would give the right answer.

Prompt B (strict): one head per answer

After adding the “one head stores one answer” rule, Llama gave every question its own correct head at temperature 0:

  • transgender, sexual orientation and ethnicity are separate
  • university, degree, graduation date, start date and location are separate
  • No question missing, none duplicated

18 of 18 grouped correctly. The cost is about 30 s more per run, because the answer is longer.

Question 3 (privacy “I agree”) was marked generate in all 10 runs, which is wrong every time. Only run 1 behaved differently. It was the first request after a pause; the most likely cause is that Ollama processes a fresh prompt slightly differently from a cached one, which can tip close calls. Close calls are exactly where the mode sits for Llama.

Recommendations

  1. Use Prompt B at temperature 0 to create the starting heads. It was the only setting with zero wrong merges.
  2. Check Llama's output in code before saving: every question id exactly once, no unknown ids, no duplicate head ids. If the check fails, retry once, then send the result to the GUI as “needs review”.
  3. Don't let Llama choose the mode. The consistency check showed it flips. Set it in code: textarea → generate, “if you selected other…” → generate, everything else → reuse. The user can change it in the GUI.
  4. Add two lines to the prompt: “never use a company name in a head id” and “if a question asks for two things, name the head after both”.
  5. Keep the GUI review step (decision 3 in the plan). Even the best run needed 4 small fixes, and approve / edit catches them in seconds.
  6. One question per head is fine at the start. Heads fill up over time as Jev puts new wordings from other companies into them.
  7. Plan for growth. 18 questions took 78 s in one call. When the database has hundreds of questions, send them in batches of about 25, together with the heads made so far.

Raw outputs of all 9 runs and the two scripts were kept outside the repo in the session scratchpad. No stored answers were sent to the model or written into this report.
